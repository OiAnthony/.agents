# design-doc：技术方案、设计文档、RFC、ADR

适用：方案还没定或刚定，需要评审、拍板、对齐。读者要判断「该不该这么做」。

## 1. 选模式

| 模式 | 用在 | 模板 |
|---|---|---|
| 评审方案 | 方向已定，要评审细节、排期、风险 | `writing-technical-design` 的 `assets/技术方案设计.md` |
| 架构探索 | 方向未定，比较多条路线 | `writing-technical-design` 的 `assets/架构探索.md` |
| ADR-lite | 一个已做出的决定，需要留档 | 本文第 4 节 |
| 小改动方案 | 一两天的改动，一页纸 | 本文第 3 节 |

正式评审优先用 `writing-technical-design`，它的硬规则（先权衡再模块、一节一结论、图号对应章节、可验证）照用。本文件补充 Web 全栈的检查项和短格式。

## 2. 每份设计文档都要有

| 节 | 写什么 | 常见缺失 |
|---|---|---|
| 背景和问题 | 现状、痛点、数字 | 只有「体验不好」，没有数据 |
| 目标 | 可验证的目标，带指标 | 目标写成手段（「引入 Redis」） |
| 关键假设 | 哪些前提若错会推翻方案，以及怎么验证 | 默认当成事实 |
| 非目标 | 读者会误以为在范围内、但这次不做的 | 列一堆无关的事凑数 |
| 方案 | 机制、数据流、接口、存储 | 只有模块图，没有数据流 |
| 备选方案 | 至少一个认真考虑过的备选，和否决理由 | 稻草人备选 |
| 权衡 | 选了什么、放弃了什么、代价是什么 | 只有优点 |
| 上线和回滚 | 灰度步骤、开关、回滚条件和操作 | 「出问题就回滚」 |
| 可观测性 | 加哪些指标、日志、告警，怎么知道成功了 | 没有 |
| 安全和隐私 | 权限、鉴权、数据暴露面、PII | 没有 |
| 开放问题 | 需要评审者决定的事 | 把已决定的事写成问题 |

## 3. 小改动方案（一页）

```markdown
# 〈结论式标题：用 X 解决 Y〉

**问题**：一两句，带数字。
**方案**：三五句，讲机制。必要时一张图。
**为什么不用 〈备选〉**：一两句。
**影响面**：改哪些服务、表、接口；是否兼容。
**上线**：开关名、灰度比例、回滚方式。
**怎么验证**：指标或测试。
**需要你决定**：〈问题〉
```

## 4. ADR-lite

```markdown
# ADR-〈编号〉：〈决定，写成一句话〉

- 状态：提议 / 已接受 / 已废弃（被 ADR-〈n〉 取代）
- 日期：YYYY-MM-DD
- 决策人：

## 背景
当时的约束和问题。

## 决定
我们决定……

## 考虑过的方案
| 方案 | 优点 | 代价 | 结论 |
|---|---|---|---|

## 后果
变容易的事；变困难的事；需要后续跟进的事。
```

## 5. 权衡怎么写

- 用表格：方案 × 维度（复杂度、延迟、成本、一致性、迁移代价、团队熟悉度）。维度只选对本次决定有影响的。
- 每个方案写清代价，被选中的方案也要写。
- 把张力写成两个极端：「每个请求都查库：一致但慢；全量缓存：快但会读到 30 秒前的数据。我们选 5 秒 TTL + 写后失效。」

## 6. Web 全栈专项检查

- [ ] **接口**：新增或变更的 API 是否向后兼容？版本策略？见 `api-doc.md`。
- [ ] **数据**：表结构变更走 expand/contract 吗？锁表风险？回填怎么做？见 `schema-doc.md`。
- [ ] **前端**：加载、空、错误三种状态；首屏性能预算；老版本客户端（App、缓存的 JS）怎么兼容。
- [ ] **缓存**：失效策略；缓存穿透和击穿；多级缓存的一致性。
- [ ] **异步**：消息丢失、重复、乱序时的行为；幂等键。
- [ ] **鉴权**：谁能调用、谁能看到哪些数据；越权检查放在哪一层。
- [ ] **限流和降级**：依赖挂了怎么办。
- [ ] **成本**：新增的云资源、第三方调用、模型 token。
- [ ] **迁移**：存量数据、存量用户、灰度期间新旧并存。

## 7. 检查清单

- [ ] 目标可验证。
- [ ] 至少一个真实备选及否决理由。
- [ ] 权衡写了被选方案的代价。
- [ ] 选中方案的已知负面结果和不覆盖的范围单独写出。
- [ ] 回滚步骤具体到开关名或命令。
- [ ] 有可观测性方案。
- [ ] 开放问题是真正需要评审者决定的。
- [ ] 标题都是结论；每节一个结论。
