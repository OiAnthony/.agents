# benchmarks：标杆文章拆解

## DeepSeek Harness：Super-agent 设计探索

链接：https://mp.weixin.qq.com/s/zoS7GlReWPhfCjENGxXCdg（X 上的发布帖 https://x.com/DeepSeekHarness/status/2116857257245987236 抓取失败，未核实内容）

结构：
1. 开头一行声明：这是架构思路探讨，不是产品介绍。先定下读者预期。
2. 引子：单任务 Agent 已经可用 → 新形态 → 缺口（以 Session 为单位，一个人能跟踪的会话只有 3–5 个；单任务上限看模型，多任务上限看人的注意力）→ 朴素解法为什么不行 → 给概念命名 → 内部演示截图 → 4 条可检验的特征，每条配具体例子 → 5 个模块对应第 2–6 节，总图标号 [2]–[6] 对应章节。
3. 每节标题是完整的判断句。
4. 权衡写成两个极端：全部放进一个会话（连续但吞吐低）对每个事件开一个会话（吞吐高但碎片化）→ 拆成 Router 和 Worker 两层。
5. 借用经典计算机概念（批处理、分片、快慢路径、局部性、推测执行、存算分离、看门狗），每个当场映射到本系统。
6. 和相邻概念划清界限：Agent Team；Anthropic 的「大脑和手」解耦。说清相同和不同。
7. 现状如实：「已实现但尚未默认开启」「以下结果仅作为初步参考」。
8. 实验：负载量化（约 300 条消息、约 20 个工作请求、5 次运行，把编码换成只耗时的工具，测的是调度而不是模型能力）；4 个变体含消融和两个提示词基线（提示词原文给出）；p50 12.4 分钟、p95 15.7 分钟，对照 p95 29.5 分钟；解释基线失败的原因（中性提示下模型 5 次都没有委派）；报告成本侧（缓存读取 token 2323 万 → 3177 万，+37%），包括中性结果。
9. Router 合批压测：请求速率 1 → 40 次/分钟，平均批大小 1.0 → 2.8，单次延迟 2.5 s → 3.9 s，摊薄后 6.4 s → 1.6 s。
10. 开放问题 8.1–8.4：扩展性、会话之后的人机交互、上下文边界与 A2A、安全和隐私。
11. 结尾：没有提出新理论，而是把经典工程思想用到 Agent 系统；原型仓库链接；作者和致谢。

可学：声明定预期；缺口带数字；特征可检验；模块—章节—图号三者对应；判断句标题；两极权衡；借概念即映射；负面结果照报；开放问题。
不学：部分长复合句；结尾一段转向愿景。

## Anthropic Engineering

**Harness design for long-running application development**（2026-03-24）
https://www.anthropic.com/engineering/harness-design-long-running-apps
- 第一人称开头，直接说遇到的两个问题和撞到的上限。
- 给失败模式命名（context anxiety、自评过宽），并区分相近做法（reset 与 compaction）的代价。
- 把主观质量变成可打分的 4 项带权重标准，用 few-shot 校准评估器。
- 表格给出不同 harness 的耗时和成本（单 Agent 20 分钟 9 美元，完整 harness 6 小时 200 美元）。
- 消融：一次去掉一个组件。原则：harness 的每个组件都编码了一个「模型自己做不到什么」的假设。
- 局限写得具体，不回避。

**Building a C compiler with a team of parallel Claudes**（2026-02-05）
https://www.anthropic.com/engineering/building-c-compiler
- 开头全是数字：16 个 Agent、约 2000 个会话、2 万美元、10 万行，能在 3 种架构上编译 Linux 6.9。
- 贴出真实的 bash 循环。
- 经验写成祈使句标题（写极高质量的测试；站在模型的位置想；让并行容易）。
- 明确的局限列表，以及作者真实的担忧（是立场，不是客套）。

## 共同模式

1. 用具体问题、数字或约束开头，不用趋势。
2. 一句话定义唯一的核心术语。
3. 在讲设计之前，先讲朴素做法怎么失败。
4. 一节一个决定，标题说出决定。
5. 证据紧挨着判断：带单位的表格、消融、基线、方法论。
6. 报告成本和负面结果。
7. 明确局限和未知。
8. 链接（仓库、附录）和致谢放最后。
 
## 应用检查清单

- [ ] 开头给出问题、约束或数字，并说明文档是探索、实现还是发布。
- [ ] 朴素方案的失败、当前决定和相邻方案的边界分别写清。
- [ ] 实验给出负载、基线、变体、运行次数、指标和成本；推算值单独标记。
- [ ] 负面结果、局限和开放问题没有被愿景段落替代。
- [ ] 借用经典概念时，紧跟它在当前系统中的具体映射。
- [ ] 标杆来源的原文、检索摘要和未核实内容分开标注，不把二手数字写成已验证事实。
- [ ] 标杆文章里的数字只用来说明写法；当前文稿的结果必须来自自己的材料或实验。
