# shared：所有路由共用的规则

## 1. 写作合同

| 项 | 问自己 | 写不出来时 |
|---|---|---|
| 读者 | 谁读？他已经知道什么？ | 默认同团队工程师，知道业务，不知道这次改动 |
| 场景 | 他在什么时候读？评审会前、上线中、排障时、搜索进来？ | 排障和上线场景：结论和命令放最前 |
| 目标 | 读完要能做什么、判断什么？ | 写不出动词，说明还没想清楚要写什么 |
| 体裁 | 路由表里的哪一个？ | 见 SKILL.md 的冲突判定 |

合同决定取舍：和目标无关的内容，写得再好也删。

## 2. 证据和判断

- 每个判断后面跟证据：数字、日志、代码位置、链接、实验条件。
- 证据分三档，写的时候分开标：**测过的**（给条件）、**引用的**（给链接）、**推测的**（写明「我们推测」「尚未验证」）。
- 数字带单位、样本量和对照：「p95 从 29.5 分钟降到 15.7 分钟（5 次运行，300 条消息负载）」，不写「大幅降低」。
- 写不出证据的判断：降调、标为假设，或删掉。
- 来源互相冲突时保留各自来源和条件，明确写「冲突未解决」；不要为了让正文顺滑而静默选一个。
- 负面结果和没做成的事照写。读者信任来自你肯说哪里不行。

### 封闭材料模式

用户说「只用我给的材料」或给了一份材料包时：
- 只用材料里的事实；材料没有的，写「材料未提及」。
- 不补常识性的「行业数据」。
- 交付时列出材料里有但你没用的内容，以及你需要但材料里没有的内容。

## 3. 术语

- 代码、命令、字段名、文件路径用反引号：`user_id`、`pnpm build`。
- 术语首次出现写「中文（English）」，例如「幂等（idempotency）」；没有通行中文译名的直接用英文，不硬译：Agent、Harness、prompt。
- 同一个概念全文只用一个词。不要为了避免重复轮换同义词（会话/对话/Session 来回换会让读者以为是三个东西）。
- 自造的名词要先定义再用，最多造一两个。

## 4. 标题

- 标题是这一节的结论，不是话题。「缓存命中率才是瓶颈」好于「性能分析」。
- 参考型文档（API、表结构）例外：标题用名词，便于查找，例如 `POST /v1/orders`。
- 中文标题不加句号；英文标题用 sentence case。
- 层级不超过三级。一节少于两段，考虑并入上一节。

## 5. 段落

- 每段只做一件事：提出一个判断，或给一组证据，或讲一个步骤。说不出这段在做哪件事，就删或拆。
- 段首句给结论，后面给依据。
- 能用表格的对比不用段落；推理过程不用列表（列表会切断因果）。
- 中文句子一般不超过 50 字；超过时检查是不是塞了两个判断。长定语（「基于……的……的……」）拆成两句。
- 句长自然变化：判断用短句，条件和因果用长句。不要为了变化而刻意变化。

## 6. 中文排版

- 中英文、中文与数字之间加空格：「部署到 Kubernetes 集群」「延迟 120 ms」。
- 中文语境用全角标点，代码和英文句子里用半角。
- 不用破折号「——」串联意思，用逗号、冒号、括号或拆句。
- 不加粗整句；加粗只给读者扫读时必须看到的词，一屏最多一两处。
- 不用 emoji 装饰标题和列表。

## 7. 改写时

- 改写前保存原稿；改完对比数字、名称、链接、代码是否一致。
- 先删后改：先删空话和重复，再调句子。
- 每轮只改一类问题，最多三轮。三轮后还不行，回到提纲找原因（通常是没想清楚要说什么）。
 
## 8. 检查清单

- [ ] 读者、使用场景和读完后的动作已经明确。
- [ ] 每个判断后都有测量条件、引用来源或明确的未验证标记。
- [ ] 数字、名称、链接和代码与原始材料逐项对过。
- [ ] 待补信息和假设单独列出，没有用套话填空。
