# everyday：PR 描述、周报、事故通报、评审意见、IM、会议纪要、邮件

共同原则：
- **结论先行（BLUF）**：第一句就是读者最需要的那句：要他做什么、结果是什么、有没有风险。
- **读者已有上下文**：不铺背景，不复述他知道的事。
- **短**：能三句说完不写五句。删掉问候和客套之外的铺垫。
- **可执行**：要别人做事时，写清楚谁、做什么、什么时候之前。

## PR 描述

模板：`assets/pr-description.md`。

- 标题：动词开头，说改了什么，例如「订单列表改用游标分页」。
- 第一段：为什么改（链接 issue），改了什么。
- 评审重点：哪里最需要看，哪里是机械改动可以略过。
- 怎么验证：跑了什么测试，截图或输出。
- 风险和回滚：影响面、开关、迁移。
- 不写「本 PR 旨在……」，不列每个文件的改动（diff 里有）。

## 周报 / 日报

```markdown
**结论**：〈一句话：本周最重要的进展或风险〉

**完成**
- 〈事〉：〈结果，带数字或链接〉

**进行中**
- 〈事〉：〈进度〉，预计〈日期〉

**风险 / 需要支持**
- 〈问题〉：需要〈谁〉在〈日期〉前〈做什么〉

**下周**
- 〈事〉
```

写结果，不写过程：「登录接口 p95 从 800 ms 降到 220 ms」好于「优化了登录接口性能」。

## 事故通报

进行中的通报（每 30 分钟或状态变化时发）：

```markdown
【P1 进行中】〈影响：什么功能、多少用户、从几点开始〉
现状：〈已知原因或排查方向〉
已做：〈止血操作〉
下一步：〈操作〉，下次更新 〈时间，带时区〉
负责人：〈名字〉
```

复盘（事后）：时间线（带时区）→ 影响（量化）→ 根因（问到第几层为什么）→ 做得好的 → 做得不好的 → 改进项（每项有负责人和日期）。对事不对人。

## 评审意见（Code review / 文档评审）

- 标明力度：`[必须]`、`[建议]`、`[疑问]`、`[nit]`。
- 说问题和原因，给具体改法或例子：「这里在循环里查库，100 条订单会发 100 次查询；改成先批量取 `user_id` 再一次 `IN` 查询。」
- 问真问题，不用反问句表达不满。
- 好的地方也说，具体说。

## IM 消息

- 一条消息说完一件事，不发「在吗」。
- 100 字或三句以内；超过就发文档链接加一句摘要。
- 要回复的写清楚问题和截止时间：「今天 18:00 前能确认吗：灰度从 10% 提到 50%？」
- 给选项比开放问题快：「A 还是 B？我倾向 A，因为……」

## 会议纪要

```markdown
**决定**
- 〈决定〉（决策人）

**待办**
| 事项 | 负责人 | 截止 |
|---|---|---|

**未决问题**
- 〈问题〉：下次〈谁〉带〈什么〉来讨论
```

只记决定、待办和未决问题，不记流水账。

## 邮件

- 主题行写结论或请求：「请在周五前确认 Q3 预算：服务器费用增加 12%」。
- 第一段：请求或结论。第二段：必要的背景。最后：明确的下一步。
- 收件人只放需要行动的人，知会的放抄送。

## 检查清单

- [ ] 第一句是结论或请求。
- [ ] 删掉了读者已知的背景和客套铺垫。
- [ ] 要别人做的事有人、有动作、有时间。
- [ ] 时间带时区。
- [ ] 数字、影响范围和状态有来源，未知项明确标为未确认。
