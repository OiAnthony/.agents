# 用 Router/Worker 合批，把调度层的等待换成请求级吞吐

> 这是一次内部调度层探索，不是对其他负载或更大规模的产品承诺。文中的实验只覆盖固定负载和 5 次运行。

一个人同时跟踪 3–5 个会话就接近上限。对内部 Agent 编排器来说，问题不只是单次模型调用有多快，还包括多个工作请求怎样一起进入模型调用。我们增加了 Router/Worker 调度层，让 Router 在 2.5 秒窗口内合批，Worker 处理合批后的请求。

在固定负载下，平均每批有 2.8 个请求。单次模型调用从 2.5 秒增加到 3.9 秒，但摊到每个请求是 1.6 秒。共享前缀缓存 token 从 2323 万增加到 3177 万。5 次运行中，新方案的 p50 是 12.4 分钟，p95 是 15.7 分钟；对照组的 p95 是 29.5 分钟。这些数字说明合批改变了等待和调用的分摊方式，但不能直接外推到其他负载。

这个调度层有四个可检验的特征：

1. **Router 等待固定窗口再合批**：窗口是 2.5 秒，平均每批 2.8 个请求。
2. **Worker 用一次调用承载一批请求**：单次调用变慢，但请求级耗时低于单次调用耗时。
3. **提示词前缀需要保持稳定**：共享前缀缓存 token 才能从 2323 万增加到 3177 万；材料没有提供缓存命中率。
4. **低负载会支付等待代价**：请求不足以快速形成批次时，合批窗口会额外等待 2.5 秒。

## 1. 逐请求处理的粒度太细，无法利用请求之间的重叠

朴素做法是让工作请求分别进入模型调用。它的优点是请求不需要等其他请求，路径也更直接；代价是每个请求都单独承担一次调用开销，编排器还要分别跟踪更多活动路径。一个人同时跟踪 3–5 个会话就接近上限，说明这种处理方式很快遇到操作上的上限。

Router/Worker 调度层把粒度从“一个请求一次调用”改成“一个时间窗口内的一批请求”。Router 先等待 2.5 秒并收集请求，再交给 Worker。这样做没有消除等待，只是把等待换成了形成批次的机会。实验中的平均批大小是 2.8 个请求，因此这个取舍可以在请求之间分摊一次模型调用。

## 2. Router 选择 2.5 秒窗口，换取批次大小但牺牲低负载即时性

Router 面临两个直接的代价。窗口太短，批次可能很小，合批带来的分摊有限；窗口太长，已经到达的请求会等待更久。当前方案固定使用 2.5 秒窗口，实验得到的平均批大小是 2.8 个请求。

低负载时，这个选择会更明显地偏向批处理：请求可能额外等待完整的 2.5 秒。材料没有给出低负载下的 p50 或 p95，因此不能判断这个等待在总耗时中占多大比例。当前也还没有决定如何自动缩短低负载窗口。

这里的 Router 只说明调度边界和窗口行为。材料没有提供队列、优先级、超时或重试策略，因此这些都不应从这次设计中推断出来。

## 3. Worker 接受更慢的单次调用，换取更低的请求级分摊

Worker 的取舍可以用两组时间表达。合批后，单次模型调用从 2.5 秒变成 3.9 秒，这是单次调用层面的负面结果。另一方面，平均每批包含 2.8 个请求，摊到每个请求是 1.6 秒。这里的 1.6 秒采用实验记录中的请求级口径，不用 3.9 秒和 2.8 个请求重新推算。

因此，“调用更快”不是这次设计的目标。目标是让单次调用服务多个请求，观察请求级结果是否更好。固定负载的端到端结果支持这一点：新方案 p50 为 12.4 分钟，p95 为 15.7 分钟；对照组 p95 为 29.5 分钟。由于材料没有提供对照组 p50、方差或每次运行的原始结果，结论只到这个范围为止。

## 4. 共享前缀缓存提供了收益，但也限制了适用条件

合批之外，实验还记录了共享前缀缓存 token 从 2323 万增加到 3177 万。这个结果与提示词前缀稳定这一条件相关：当前方案依赖稳定的 prompt prefix，材料没有说明具体的缓存命中率，也没有提供去掉缓存后的消融结果。

这带来一个边界。只要提示词前缀稳定，缓存 token 的增加可以作为这次实验的观测结果；但不能据此断言所有请求都能获得同样收益。当前材料也不足以把端到端时延改善单独归因于合批或缓存中的某一个组件。

## 5. 它和逐请求调用的区别在于调度粒度

| 维度 | 逐请求处理 | Router/Worker 调度层 |
|---|---|---|
| 调度粒度 | 一个请求一次处理 | 2.5 秒窗口内合批 |
| 单次模型调用 | 2.5 秒 | 3.9 秒 |
| 请求级分摊 | 材料未提供 | 1.6 秒 |
| 批次规模 | 不适用 | 平均 2.8 个请求 |
| 低负载行为 | 不需要等待合批窗口 | 可能额外等待 2.5 秒 |
| 对提示词前缀的要求 | 材料未说明 | 依赖前缀稳定 |

两者都处理工作请求。区别不是增加一个新的业务请求类型，而是改变请求进入模型调用的时间边界和批次边界。至于队列实现、Worker 数量和调度公平性，材料没有涉及，本文不做补充。

## 6. 实验显示 p95 改善，但实验口径仍然有限

实验使用固定负载：300 条消息、20 个工作请求，运行 5 次。已知的对比结果如下：

| 配置 | 单次模型调用 | 摊到每个请求 | 共享前缀缓存 token | p50 | p95 |
|---|---:|---:|---:|---:|---:|
| 对照组 | 2.5 秒 | 材料未提供 | 2323 万 | 材料未提供 | 29.5 分钟 |
| 新方案 | 3.9 秒 | 1.6 秒 | 3177 万 | 12.4 分钟 | 15.7 分钟 |

这组结果回答了一个有限的问题：在给定的 300 条消息、20 个工作请求和 5 次运行中，增加合批调度后，记录到的新方案 p50 和 p95 是多少。它没有回答低负载、其他批大小或更大消息量下的表现。

成本也需要拆开看。已知成本包括单次模型调用从 2.5 秒增加到 3.9 秒，以及低负载时额外等待 2.5 秒；已知资源观测包括共享前缀缓存 token 从 2323 万增加到 3177 万。材料没有提供金额成本、模型版本、硬件、并发配置、运行方差或消融结果，因此不能把 token 变化换算成费用，也不能计算各模块的独立贡献。

## 7. 低负载窗口和前缀变化是下一轮实验的重点

- **如何自动缩短低负载窗口？** 固定 2.5 秒能形成平均 2.8 个请求的批次，但低负载时会直接增加 2.5 秒等待。当前还没有决定自动缩短窗口的方式，也没有相应实验数据。
- **提示词前缀变化后，缓存收益还剩多少？** 当前方案依赖前缀稳定，已知数据只有共享前缀缓存 token 的变化，没有缓存命中率或前缀变化场景的结果。
- **结论能否扩展到其他负载？** 当前只给出了 300 条消息、20 个工作请求、5 次运行的结果。更低或更高负载下的批大小、等待和 p95 尚未提供。

## 现状

材料表明，新方案已经完成一次固定负载实验，并记录了 Router 的 2.5 秒合批窗口、平均批大小、模型调用时间、共享前缀缓存 token 和端到端分位数。材料没有说明代码位置、是否默认启用、部署范围或低负载窗口的自动调整方案。本文的结论限于已给出的实验条件。
