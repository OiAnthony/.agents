# 用 Router/Worker 调度层降低 Agent 编排的跟踪负担

当一个人同时跟踪 3–5 个会话时，继续让每个工作请求独立推进，会很快接近人的跟踪上限。我们为内部 Agent 编排器增加了一层 Router/Worker 调度层，目标不是让单次模型调用更快，而是把多个请求放到同一个调度节奏中处理。

本文只讨论这次实验中已经观察到的行为和结果，不把它们扩展为更普遍的结论。

## 朴素方案为什么不够

朴素方案可以理解为：每个工作请求分别触发一次模型调用，调用之间不做合批。它的特点是单个请求可以直接开始，但多个会话同时推进时，人仍然需要分别跟踪这些请求的状态。

在一个人同时跟踪 3–5 个会话就接近上限的情况下，这种方式没有解决调度问题。它把请求处理拆散了，也没有利用请求之间可能共享的提示词前缀。

这并不意味着独立调用在所有场景都不可用。相反，低负载时，等待其他请求加入合批窗口可能比立即处理更慢。问题在于：当请求数量增加时，只依赖独立调用，无法利用合批和共享前缀缓存带来的机会。

## Router/Worker 的基本设计

新方案增加 Router/Worker 调度层，并按 2.5 秒窗口对请求合批。

可以用两个角色理解这层设计：

- **Router**：在 2.5 秒窗口内收集到达的工作请求，并把它们组成批次。
- **Worker**：处理 Router 形成的批次，并完成对应的模型调用。

这两个角色的关键不是增加更多处理步骤，而是改变请求进入模型调用的方式：请求不再完全各自独立地调用模型，而是先经过一个有边界的合批窗口。

在固定负载实验中，平均每批包含 2.8 个请求。这个数值说明，在该实验负载下，窗口确实把多个请求放到了同一批中；它不代表其他负载下也会得到相同的批大小。

### 为什么合批会影响缓存

共享前缀缓存 token 从 2323 万增加到 3177 万。当前观察到的结果与提示词前缀稳定有关：缓存依赖提示词前缀稳定，前缀发生变化时，不能假设能得到同样的缓存收益。

因此，Router/Worker 的设计同时带来两个依赖：

1. 请求需要在窗口内聚合，才有机会形成更大的批次。
2. 提示词前缀需要保持稳定，缓存收益才有依据。

## 延迟与调度成本的权衡

合批不是没有成本。单次模型调用从 2.5 秒变成 3.9 秒，表面上看单次调用变慢了。但如果把调用时间摊到批内请求上，平均每个请求是 1.6 秒。

这两个数字描述的是不同口径：

- **单次模型调用耗时**：从 2.5 秒增加到 3.9 秒。
- **按请求摊销后的耗时**：平均每个请求为 1.6 秒。

因此，不能只看单次调用耗时来判断这次设计的效果。合批用更长的单次调用换取了批内请求的摊销；同时，Router 还引入了最多 2.5 秒的窗口等待成本。

低负载时，这个成本尤其明确：如果窗口内没有足够请求，系统仍会额外等待 2.5 秒。当前还没有决定如何自动缩短低负载窗口，所以这部分行为仍是开放的设计问题，而不是已经解决的能力。

## 实验口径

本次实验使用固定负载，具体口径如下：

- 消息数：300 条
- 工作请求数：20 个
- 运行次数：5 次
- 合批窗口：2.5 秒
- 平均每批请求数：2.8 个

在这个口径下，新方案的整体运行时间指标为：

- p50：12.4 分钟
- p95：15.7 分钟

对照组的 p95 为 29.5 分钟。也就是说，在这组固定负载和 5 次运行的实验中，新方案的 p95 低于对照组的 p95。

这里没有提供对照组的 p50，因此不能据此比较两组的 p50。实验次数为 5 次，也不支持把结果直接解释为所有工作负载下都成立的普遍规律。

## 成本与收益应如何一起看

这次设计的成本和收益分别落在不同层面：

### 成本

- 每个合批窗口可能带来额外 2.5 秒等待。
- 单次模型调用从 2.5 秒增加到 3.9 秒。
- 低负载时，窗口可能没有足够请求，却仍产生等待。
- 缓存收益依赖提示词前缀稳定，前缀变化会削弱这一依赖带来的确定性。

### 收益

- 在固定实验负载下，平均每批有 2.8 个请求。
- 按请求摊销后，单个请求对应的调用时间为 1.6 秒。
- 共享前缀缓存 token 从 2323 万增加到 3177 万。
- 新方案的 p50 为 12.4 分钟，p95 为 15.7 分钟；对照组 p95 为 29.5 分钟。

这些结果不能简化成“合批总是更快”。更准确的说法是：在给定的固定负载和实验口径下，合批带来了批内摊销、更多共享前缀缓存 token，以及更低的新方案 p95；同时，它引入了窗口等待和更长的单次调用时间。

## 负面结果

负面结果不是边缘情况，而是这个设计必须正面处理的部分：

1. **低负载会等待。** 2.5 秒窗口在低负载时可能无法被足够请求填满，造成额外等待。
2. **单次调用变慢。** 单次模型调用耗时从 2.5 秒增加到 3.9 秒。只观察单次调用时延，会看到明显的回归。
3. **缓存依赖前缀稳定。** 共享前缀缓存 token 的增加不能脱离提示词前缀稳定这一条件来理解。
4. **实验覆盖有限。** 目前给出的口径只有 300 条消息、20 个工作请求和 5 次运行，不能据此推断其他负载下的表现。

## 局限

当前数据有几个明确的边界：

- 只给出了对照组 p95，没有给出对照组 p50，因此不能完整比较两个分位数。
- 运行次数为 5 次。这个样本可以记录本次实验结果，但不能单独支撑更广泛的性能结论。
- 平均批大小 2.8 个请求只对应当前实验负载。低负载时合批行为可能不同，但现有事实没有提供更多低负载数据。
- 现有结果说明缓存 token 数量从 2323 万增加到 3177 万，但没有提供由此带来的其他成本指标，因此不能进一步换算成本节省。
- 低负载窗口的自动缩短策略尚未决定，所以当前方案还没有覆盖这个调度问题。

## 开放问题

最直接的开放问题是：**低负载时，如何自动缩短 2.5 秒合批窗口？**

这个问题需要在两类目标之间作出选择：

- 更快开始处理，减少低负载下的窗口等待。
- 保留等待机会，以形成更大的批次并利用共享前缀缓存。

目前还没有决定采用哪种自动缩短方式，也没有足够事实说明某种方式在不同负载下更好。因此，下一步不应把某个具体策略当成既定实现，而应继续用明确的负载和测量口径比较它们。

## 结语

Router/Worker 调度层改变的是请求进入模型调用的节奏。它用 2.5 秒窗口把请求合批，在固定实验负载下得到平均 2.8 个请求一批，并让共享前缀缓存 token 从 2323 万增加到 3177 万。与此同时，单次模型调用从 2.5 秒变为 3.9 秒，低负载时还会额外等待 2.5 秒。

在 300 条消息、20 个工作请求、运行 5 次的固定实验中，新方案的 p50 为 12.4 分钟、p95 为 15.7 分钟，对照组 p95 为 29.5 分钟。这个结果支持我们继续研究调度层，但它不构成对所有负载的普遍承诺。特别是低负载窗口如何自动缩短，以及提示词前缀稳定性如何持续满足，仍然是需要解决的开放问题。
