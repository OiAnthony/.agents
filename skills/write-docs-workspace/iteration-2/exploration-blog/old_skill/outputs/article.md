# Router/Worker 调度层把给定负载的 p95 从 29.5 分钟降到 15.7 分钟

> 本文是一篇基于有限实验材料的探索记录，不是对更大规模负载的产品承诺。除特别说明外，文中的事实只来自题给材料。

当一个人同时跟踪 3–5 个会话时，就接近可处理的上限。对内部 Agent 编排器来说，继续让人直接跟踪每个会话和工作请求，无法把这个上限变成可调度的系统能力。我们增加了 Router/Worker 调度层，让请求进入 2.5 秒窗口并合批。固定负载下，平均每批有 2.8 个请求；单次模型调用从 2.5 秒变成 3.9 秒，但按题给口径摊到每个请求是 1.6 秒。新方案的 p95 为 15.7 分钟，对照组为 29.5 分钟。

这个结果有明确边界：实验只覆盖 300 条消息、20 个工作请求和 5 次运行。低负载时，合批窗口会额外等待 2.5 秒；共享前缀缓存又依赖提示词前缀稳定。我们还没有决定如何自动缩短低负载窗口。

## 朴素方案在 3–5 个会话处接近上限

朴素方案把会话和工作请求的跟踪压力留给一个人。当同时跟踪的会话达到 3–5 个时，就接近上限。这个事实说明问题首先是调度问题：请求需要在多个会话之间被组织起来，而不是只依赖人工持续跟踪。

材料没有提供朴素方案的具体实现、并发策略或每个请求的处理流程。因此，本文不把它扩展成某种未提供的队列、线程模型或优先级策略。能够确认的是，对照组在实验中的 p95 为 29.5 分钟。

## 调度层的已知边界是按窗口合批，而不是更快地完成单次调用

从材料能确认的模块关系如下：

```text
工作请求
    ↓
Router/Worker 调度层
    ↓  在 2.5 秒窗口内合批
模型调用
    ↓
共享前缀缓存的观测
```

这里的 `Router/Worker` 是调度层的名称。材料只说明该调度层按 2.5 秒窗口合批，没有说明 Router 和 Worker 各自的职责、通信方式、队列结构、失败处理或调度规则。为保持材料边界，本文不为它们补充这些实现细节。

合批带来了一项直接代价：单次模型调用从 2.5 秒增加到 3.9 秒。它换来的指标是平均每批 2.8 个请求，按题给口径摊到每个请求是 1.6 秒。换句话说，方案的取舍不是让一次模型调用更快，而是接受单次调用变慢，换取请求在调度层中的摊销。材料没有提供这两个时间的测量起止点，也没有给出 1.6 秒的具体计算方法，所以这里按原始口径记录，不自行重算。

低负载会放大另一项代价。窗口内请求不足时，请求仍可能额外等待 2.5 秒。当前材料没有说明低负载的阈值、请求到达分布，或自动缩短窗口的候选策略。

## 共享前缀缓存的收益取决于提示词前缀稳定

实验中，共享前缀缓存 token 从 2323 万增加到 3177 万。这个变化与调度层带来的请求合批同时出现，但材料没有提供缓存命中率、token 费用或二者之间的因果拆分。因此，我们只能报告缓存 token 的观测变化，不能把它直接换算成金额收益，也不能断言全部增量都由合批造成。

缓存还有一个明确条件：提示词前缀需要保持稳定。只要前缀稳定性下降，材料就没有说明缓存表现会如何变化。它因此是方案的依赖，也是需要单独验证的边界。

## 实验结果显示端到端结果改善，但实验口径仍然有限

实验使用固定负载：300 条消息、20 个工作请求，运行 5 次。结果中的 p50 和 p95 单位是分钟，但材料没有说明它们具体从哪个时间点计时到哪个时间点，也没有提供每次运行的原始值、方差或区间。

| 配置 | p50 | p95 | 可见的调用成本 | 备注 |
|---|---:|---:|---|---|
| 对照组 | 材料未提供 | 29.5 分钟 | 材料未提供 | 对照配置的其他细节未提供 |
| Router/Worker 调度层 | 12.4 分钟 | 15.7 分钟 | 单次模型调用 3.9 秒 | 平均每批 2.8 个请求；5 次运行 |

与对照组相比，新方案的 p95 从 29.5 分钟变为 15.7 分钟。新方案的 p50 为 12.4 分钟。材料没有提供对照组 p50，所以不能计算 p50 的变化。材料也没有提供消融实验，因此不能判断 2.5 秒窗口、合批或缓存观测分别贡献了多少。

成本不能只看 p95。单次模型调用从 2.5 秒变成 3.9 秒，低负载时还会额外等待 2.5 秒；另一方面，共享前缀缓存 token 从 2323 万增加到 3177 万。材料没有提供金额、总 token 消耗或模型价格，因此本文不把这些数字合并成货币成本。

这些结果只支持一个受限结论：在上述固定负载和 5 次运行的实验中，Router/Worker 调度层对应的新方案记录到了 12.4 分钟的 p50 和 15.7 分钟的 p95，而对照组记录到了 29.5 分钟的 p95。它们不能直接外推到其他负载、其他运行次数或未提供的模型与硬件条件。

## 这个方案改善了请求摊销，却保留了低负载等待

已知的收益和代价可以放在一起看：

| 维度 | 新方案的观测 | 代价或边界 |
|---|---|---|
| 合批 | 2.5 秒窗口，平均每批 2.8 个请求 | 单次模型调用从 2.5 秒变成 3.9 秒 |
| 请求摊销 | 按题给口径，每个请求是 1.6 秒 | 1.6 秒的计算口径未提供 |
| 结果时间 | p50 为 12.4 分钟，p95 为 15.7 分钟 | 对照组 p50 未提供 |
| 缓存观测 | 共享前缀缓存 token 从 2323 万增至 3177 万 | 依赖提示词前缀稳定 |
| 低负载 | — | 合批窗口会额外等待 2.5 秒 |

这组数据不支持“所有场景都更快”的结论。它只表明，在一个具体固定负载上，端到端结果和请求摊销指标向有利方向变化，同时保留了单次调用变慢、低负载等待和缓存前缀稳定性要求。

## 低负载窗口和实验覆盖范围仍未确定

1. **低负载时是否自动缩短窗口？** 当前还没有决定如何自动缩短 2.5 秒窗口。难点在于，缩短窗口可能减少等待，但材料没有提供请求到达分布或候选策略，无法判断取舍。
2. **提示词前缀变化会怎样影响缓存？** 已知缓存依赖前缀稳定，但没有提供稳定性的判定标准，也没有给出前缀变化后的测量结果。
3. **结果能否迁移到其他负载？** 当前只知道 300 条消息、20 个工作请求和 5 次运行的结果。更低或更高的负载、不同请求分布以及更多运行次数，材料都未覆盖。
4. **各模块分别贡献了什么？** 没有消融结果，无法把整体变化归因到某个组件或某个调度参数。
5. **Router 与 Worker 如何分工？** 材料没有提供二者的内部职责、失败处理或配置方式。因此，当前文章只能描述调度层的可观测行为，不能给出更细的实现说明。

在现有材料范围内，Router/Worker 调度层的结论停留在一次固定负载实验：它用 2.5 秒窗口组织请求，平均每批 2.8 个请求，并记录到 12.4 分钟的 p50 和 15.7 分钟的 p95。下一步需要先补齐低负载策略和实验口径，再判断这些结果是否适用于材料未覆盖的场景。
