# 用 2.5 秒合批降低 Agent 编排器的尾部等待

> 本文记录一次调度层探索。文中的数字只适用于给定的固定负载，不外推到更大规模或其他负载。

一个人同时跟踪 3–5 个会话就接近上限。对内部 Agent 编排器来说，工作请求的到达和处理方式因此成了实际约束。我们增加了 Router/Worker 调度层，把请求放进 2.5 秒窗口合批。固定负载下，新方案的 p95 为 15.7 分钟，对照组为 29.5 分钟；新方案的 p50 为 12.4 分钟。

这次改动也带来了明确的代价：单次模型调用从 2.5 秒变成 3.9 秒，平均每批有 2.8 个请求，摊到每个请求是 1.6 秒。低负载时，请求还会额外等待 2.5 秒。共享前缀缓存 token 从 2323 万增加到 3177 万，但这个结果依赖 prompt 前缀保持稳定。

## 1. 不加调度层的朴素路径无法解释这组尾部时间

朴素方案可以理解为不引入本文新增的调度层和 2.5 秒合批行为的对照路径。材料没有提供对照组的内部实现，因此这里不推断它的队列、并发或重试方式，只比较给出的测量结果。

在固定负载下，对照组 p95 是 29.5 分钟。新方案 p95 是 15.7 分钟，p50 是 12.4 分钟。这个差异说明，在这组工作量和 5 次运行中，新方案观察到了更短的尾部时间。它不能单独证明某一个模块造成了全部变化，因为材料没有提供 Router、Worker 或合批行为的消融结果。

朴素路径的问题还在于，它没有把请求等待和模型调用的代价放在同一个口径下观察。只看一次调用的耗时，会看到新方案从 2.5 秒升到 3.9 秒；把一个批次的代价摊到请求上，则得到 1.6 秒。两种数字都是真的，回答的是不同问题。

## 2. Router/Worker 的可确认边界是一个带窗口的调度层

材料只明确了 Router/Worker 调度层这个名称，以及它按 2.5 秒窗口合批的行为。材料没有定义 Router 和 Worker 各自的职责，所以本文不把路由规则、Worker 生命周期、队列实现或并发模型写成当前系统的事实。

已知的处理路径可以画成下面这样：

```text
20 个工作请求
        │
        ▼
Router/Worker 调度层
（按 2.5 秒窗口合批）
        │
        ▼
模型调用
```

这是一张行为边界图，不是 Router 与 Worker 的内部职责图。给出的观测是平均每批 2.8 个请求。由此可以解释为什么单次模型调用的时间和单个请求摊销时间会同时出现：一次调用承载了一个批次，而请求级数字反映的是批次代价的摊分结果。

这里的取舍很直接。窗口越长，低负载请求承担的等待越多；窗口越短，能合在一起的请求可能变少。当前材料只给出了 2.5 秒窗口和低负载下额外等待 2.5 秒，没有给出其他窗口长度的对比。因此，我们不能从这组结果判断更短窗口的收益，也不能判断它会如何影响缓存或 p95。

## 3. 合批降低请求级摊销，但牺牲了单次调用时间

新方案的单次模型调用是 3.9 秒，对照值是 2.5 秒。与此同时，平均每批 2.8 个请求，摊到每个请求是 1.6 秒。这个设计把代价从一次调用的局部时间转移到批次内的请求共享上。

这个权衡不应被简化成“调用更快”或“调用更慢”。如果指标是单次模型调用时间，新方案更慢；如果指标是材料给出的请求级摊销时间，新方案是 1.6 秒。两者的计算边界不同，不能互相替代。

低负载是这个取舍的反例。请求不足以迅速填满窗口时，2.5 秒窗口本身会成为额外等待。当前还没有决定如何自动缩短低负载窗口，所以这部分仍是开放的调度策略，而不是已验证的优化结果。

## 4. 缓存收益建立在 prompt 前缀稳定上

共享前缀缓存 token 从 2323 万增加到 3177 万。这个数字说明两种方案的缓存观测不同，但材料没有提供缓存命中率、缓存有效期或 token 统计的具体定义，因此不能把它改写成命中率提升，也不能换算成金钱成本。

材料明确指出，缓存依赖 prompt 前缀稳定。也就是说，前缀变化是新方案的已知风险条件。当前没有提供“稳定”所需的具体边界，也没有提供前缀变化时缓存 token 如何变化的实验。缓存结果因此只能和这次固定负载一起解读，不能外推成所有 prompt 都有相同收益。

## 5. 实验只支持固定负载下的有限结论

实验口径如下：固定负载包含 300 条消息和 20 个工作请求，共运行 5 次。材料没有提供硬件、模型版本、并发设置，也没有定义 p50 和 p95 的起止时间。下面保留已给出的数字，并把缺失项标出来。

| 配置 | p50 | p95 | 其他已知观测 |
|---|---:|---:|---|
| 对照组 | 材料未提供 | 29.5 分钟 | 单次模型调用 2.5 秒；共享前缀缓存 token 2323 万 |
| 新方案 | 12.4 分钟 | 15.7 分钟 | 单次模型调用 3.9 秒；平均每批 2.8 个请求；请求级摊销 1.6 秒；共享前缀缓存 token 3177 万 |

表中的时间来自同一组固定负载描述，但材料没有说明 p50/p95 是哪一种端到端时间，也没有给出 5 次运行的方差或区间。因此，本文只报告观测值，不把它们包装成精确的稳定性估计。

这组实验还没有消融结果。我们无法仅凭现有数字区分以下因素的贡献：Router/Worker 的模块边界、2.5 秒合批窗口，以及 prompt 前缀稳定带来的缓存变化。对照组也只有 p95，缺少对照 p50，所以不能比较两组完整的分布。

成本同样需要分层看待。时间成本包括单次模型调用从 2.5 秒到 3.9 秒的变化，以及低负载下额外的 2.5 秒等待。请求级数字是 1.6 秒。材料没有提供 token 价格、调用费用或总运行时费用，因此本文不报告金额成本。

## 6. 这次结果能迁移的只有测量方法，不能直接迁移数字

第一，单次调用和请求级摊销必须同时记录。前者展示一次模型调用的局部代价，后者展示合批后请求如何分摊代价。只报告其中一个，会漏掉另一面的权衡。

第二，p50 和 p95 需要和负载、运行次数一起出现。本文的 12.4 分钟和 15.7 分钟只对应 300 条消息、20 个工作请求和 5 次运行。材料没有覆盖更大负载，也没有提供方差，因此不能把这组数字写成普遍性能结论。

第三，缓存指标必须带前提。这里的共享前缀缓存 token 从 2323 万变成 3177 万，但收益依赖 prompt 前缀稳定。没有前缀变化实验，就不能判断该结果在其他提示词下是否成立。

## 7. 还有四个问题没有答案

1. **低负载时窗口应缩短到多少？** 当前还没有自动缩短策略，也没有其他窗口长度的实验。缩短窗口可能减少额外等待，但材料没有给出它对批大小、模型调用时间或缓存的影响。
2. **prompt 前缀需要多稳定才能保留缓存收益？** 已知缓存依赖前缀稳定，未知的是稳定性的具体边界，以及前缀变化后 3177 万 token 这一观测会如何变化。
3. **Router 和 Worker 分别贡献了什么？** 材料没有给出模块职责定义，也没有分别移除或替换它们的结果。当前不能把整体 p95 差异归因给某个模块。
4. **这组测量的波动范围是多少？** 已知运行了 5 次，未知的是每次结果、方差和置信区间。对照组还缺少 p50，因此完整分布比较仍待补充。

目前可以确认的是一组固定负载下的观测：300 条消息、20 个工作请求、5 次运行，以及对应的 p50、p95、调用时间、请求级摊销和缓存 token。材料没有说明代码是否默认启用、部署在哪里或是否已经覆盖其他负载，所以本文不对这些状态作进一步判断。
