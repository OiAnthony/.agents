# howto：教程、操作指南、README、Runbook

适用：读者要动手做事。依据 Diátaxis 框架先判断是哪一类。

## 1. Diátaxis 罗盘

| | 读者在学习（获取能力） | 读者在干活（应用能力） |
|---|---|---|
| **行动** | Tutorial 教程 | How-to 操作指南 |
| **认知** | Explanation 解释 | Reference 参考 |

两个问题定位：读者在做事还是在理解？在学还是在干活？一篇文档只做一种。混在一起时拆开，互相链接。

- **Tutorial**：带新手走完一次，保证成功。路线由你定，不给选择，不解释原理（链接到 explanation）。
- **How-to**：读者有明确目标和基础。只写达成目标的步骤，可以有分支（「如果你用 Docker……」）。
- **Reference**：查的。见 api-doc、schema-doc。
- **Explanation**：为什么。可以是设计文档或博客。

## 2. How-to 模板

```markdown
# 如何〈完成某个具体目标〉

〈一句话：做完之后你会得到什么。〉

## 前提
- 版本、权限、已安装的工具、预计耗时

## 步骤
1. 〈动词开头的一步〉
   ```bash
   命令
   ```
   预期输出：`...`
2. ...

## 验证
怎么确认成功。

## 常见问题
| 现象 | 原因 | 解决 |
|---|---|---|
```

步骤规则：
- 一步一个动作，动词开头：「运行」「打开」「把 X 改成 Y」。
- 条件放在动作前：「如果用 macOS，运行……」。
- 每个命令后写预期输出或怎么判断成功。
- 命令能直接复制运行；需要替换的值用 `<尖括号>` 并说明。
- 输出不稳定时写可观察的不变量或状态，不把一次偶然的完整输出当成唯一成功标准。
- 不写「简单地」「只需」「轻松」。

## 3. Tutorial 额外要求

- 开头写清最终成果，最好有截图或输出。
- 每几步给一个可见的结果，让读者确认没走偏。
- 从干净环境实测一遍。

## 4. README

顺序：一句话说这是什么 → 快速开始（最多 5 步能跑起来）→ 常用操作 → 配置 → 开发和测试 → 链接到更多文档。
快速开始必须在干净环境验证过。

## 5. Runbook（值班手册）

读者在半夜被告警叫醒，压力大、上下文少。模板：`assets/runbook.md`。

- 第一屏：这个告警意味着什么、影响谁、多紧急。
- 先止血，后排查：先写缓解操作（回滚、切流、扩容、关开关），再写诊断步骤。
- 每个操作给可复制的命令和预期结果；危险操作标出来，写回退方法。
- 写明何时升级、找谁。
- 每次事故后更新。

## 6. FAQ

FAQ 常是没整理好的文档。能归入指南或参考的问题，移过去。保留的问题用读者的原话，答案第一句直接回答。

## 7. 检查清单

- [ ] 确定了 Diátaxis 类型，没有混写。
- [ ] 前提条件完整（版本、权限、耗时）。
- [ ] 每步一个动作，动词开头，有预期结果。
- [ ] 命令在干净环境实测过。
- [ ] 有验证步骤和常见问题。
- [ ] Runbook 先止血后排查，有升级路径。
