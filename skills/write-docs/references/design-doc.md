# design-doc：技术方案、设计文档、RFC、ADR

适用：方案还没定或刚定，需要评审、拍板、对齐或留档。读者要判断「该不该这么做」以及「如何安全落地」。

## 1. 先选模式

| 模式 | 何时用 | 最小交付 |
|---|---|---|
| 评审方案 | 方向已定，要评审细节、排期、风险和落地 | 背景、目标、方案、备选、权衡、风险、上线与验证 |
| 架构探索 | 方向未定，要比较路线、验证主张和边界 | 瓶颈、可检验特征、权衡、机制、验证、开放问题 |
| ADR-lite | 决定已经做出，需要保留上下文 | 背景、决定、考虑过的方案、后果 |
| 小改动方案 | 一两天内完成的一页纸改动 | 问题、方案、备选、影响面、上线、验证、待决定项 |

用户没有说明时：有评审、排期或落地语境，默认「评审方案」；有探索、原型或路线比较语境，默认「架构探索」。如果两者都会影响结构，只问「要评审定稿，还是比较路线？」。

## 2. 硬规则

1. **先权衡，后模块。** 至少写一条 Trade-off：选项、代价、选择和理由齐全后，才展开模块。
2. **一节一个结论。** 每节开头用短断言说明本节要证明什么；两个结论拆成两节。
3. **目标必须可验证。** 目标写结果和指标，不写成手段，例如不要只写「引入某组件」。
4. **目标和非目标成对出现。** 非目标只列读者可能误以为本次包含的事项。
5. **模块必须有边界。** 每个模块写职责、输入、输出和明确不做。
6. **图服务论证。** 总图的编号与章节对应；每张图都说明它回答的问题。机制简单时不用图。
7. **事实和假设分开。** 关键假设写出验证方式；未知内容标为待补，不用常识填空。
8. **短句优先。** 条件和动作放表格；删除空泛口号和没有证据的程度词。

## 3. 必备内容

| 节 | 写什么 | 常见缺失 |
|---|---|---|
| 背景和问题 | 现状、约束、痛点和影响 | 只有「体验不好」，没有数据或例子 |
| 目标与非目标 | 可验收的结果和明确边界 | 把实现手段当目标 |
| 关键假设 | 哪些前提若错会推翻方案，以及怎么验证 | 默认把假设当事实 |
| 方案 | 主路径、数据流、接口、存储和边界 | 只有模块图，没有路径 |
| 备选方案 | 至少一个认真考虑过的路线和否决理由 | 稻草人备选 |
| 权衡 | 选了什么、放弃了什么、代价是什么 | 只写优点 |
| 上线和回滚 | 灰度、开关、回滚条件和具体操作 | 只写「出问题就回滚」 |
| 可观测性 | 指标、日志、告警和成功判据 | 没有验证入口 |
| 安全与隐私 | 权限、鉴权、数据暴露面和敏感数据 | 只描述正常路径 |
| 开放问题 | 仍需评审者决定的事项 | 把已决定的事写成问题 |

## 4. 评审方案的短格式

```markdown
# 〈结论式标题：用 X 解决 Y〉

**问题**：一两句，带约束或数字。
**目标 / 非目标**：这次要达到什么，明确不做什么。
**方案**：三到五句，讲机制、主路径和边界。
**为什么不用 〈备选〉**：说明代价和否决理由。
**影响面**：改哪些服务、表、接口或流程；是否兼容。
**上线与回滚**：开关、灰度、回滚条件和操作。
**怎么验证**：指标、测试或可观察结果。
**需要评审者决定**：仍未关闭的问题。
```

## 5. 架构探索的结构

1. 一句话瓶颈：今天限制进一步提升的是什么，不是什么。
2. 形态定义：列 3–5 条可检验特征，每条都有可观察表现。
3. 总图与模块地图：模块编号必须对应后文；每节只解决一个权衡。
4. 每节按「两个极端 → 机制 → 选择 → 证据 → 剩余代价」展开。
5. 验证：只证明架构主张，写清怎么证伪、当前结果和未测项。
6. 开放问题：说明为什么现在不能关闭，以及可能方向。
7. 原型指针：正文结束后再给仓库、实现状态和未覆盖范围。

## 6. 权衡怎么写

用表格表达方案与维度。维度只选影响本次决定的项，例如复杂度、延迟、成本、一致性、迁移代价、可维护性、团队熟悉度。

| 方案 | 得到 | 失去 | 适用条件 | 结论 |
|---|---|---|---|---|
| 方案 A | [收益] | [代价] | [条件] | 选 / 不选 |
| 方案 B | [收益] | [代价] | [条件] | 选 / 不选 |

不要只写「方案 A 更好」。要写出选中的方案承担了什么代价，以及什么证据会推翻当前选择。

## 7. 领域专项检查

只加入与当前决定相关的维度：

- **接口**：兼容性、版本策略、错误处理和调用方迁移。
- **数据**：迁移顺序、锁与回填、校验、回滚和新旧结构并存。
- **交互**：加载、空、错误状态，性能预算和旧客户端兼容。
- **异步**：丢失、重复、乱序、幂等、重试和死信。
- **权限**：谁能调用、谁能看到什么、越权检查在哪一层。
- **依赖**：限流、降级、超时、故障隔离和恢复条件。
- **成本**：新增资源、第三方调用、存储和运行成本。
- **迁移**：存量数据、存量用户、灰度期间新旧版本共存。

## 8. 检查清单

- [ ] 开篇有一句问题或瓶颈。
- [ ] 目标可验证，非目标明确。
- [ ] 至少一个真实备选及否决理由。
- [ ] 权衡写了被选方案的代价。
- [ ] 关键假设有验证方式。
- [ ] 模块有输入、输出和明确不做。
- [ ] 图与章节编号对齐，并说明图要回答的问题。
- [ ] 上线和回滚具体到条件、开关或操作。
- [ ] 有可观测性、安全与隐私检查，或说明不适用。
- [ ] 开放问题是真正需要评审者决定的事。
- [ ] 标题都是结论；每节一个结论。
