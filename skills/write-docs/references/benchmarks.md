# benchmarks：技术文章结构与证据参考

本文件只总结可迁移的写法，不提供当前任务的事实，也不绑定某个领域、产品或模型。需要模仿具体作者时，另行读取用户提供的样例并制作风格卡。

## 1. 可迁移的文章结构

1. **先定预期**：开头说明这是探索、实现复盘、发布说明还是研究报告。
2. **具体缺口**：用场景、数字或约束说明为什么要做，不用泛泛趋势开头。
3. **定义术语**：只定义本文真正需要的一个或几个概念。
4. **先讲朴素方案**：说明它在哪里失败，再引出当前方案。
5. **一节一个决定**：标题直接说出本节结论；机制、证据和剩余代价紧跟其后。
6. **模块与章节对应**：总图、模块编号和正文顺序一致；每张图说明它回答的问题。
7. **把概念落到当前系统**：借用已有工程概念时，立即说明映射关系和不适用之处。
8. **结果可复核**：给出负载、基线、变体、运行次数、指标定义和成本。
9. **照报负面结果**：失败、退化、未测项和不确定性不能被愿景段落替代。
10. **开放问题收尾**：写仍未关闭的问题、下一步验证或复现指针，然后停止。

## 2. 证据与边界

- 实测、推算、引用和假设分开标记。
- 每个数字带单位、样本量、对照和测量条件。
- 基线失败时解释失败原因，不把失败直接当成方案收益。
- 只报告材料或实验支持的结论，不把单次结果包装成普遍规律。
- 参考样例只提供结构和表达方式；其中的数字、观点、架构和专有名词不自动成为当前文稿事实。

## 3. 应用检查清单

- [ ] 开头给出问题、约束或数字，并说明文档类型。
- [ ] 朴素方案的失败、当前决定和相邻方案的边界分别写清。
- [ ] 每个标题是结论，每节只有一个结论。
- [ ] 证据紧挨判断，实验给出方法论和成本。
- [ ] 负面结果、局限和开放问题没有被愿景段落替代。
- [ ] 图、表和引用都有明确用途。
- [ ] 当前文稿的事实全部来自任务材料、可核实来源或实际实验。
