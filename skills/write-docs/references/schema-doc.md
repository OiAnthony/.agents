# schema-doc：表结构、数据字典、迁移说明

适用：新建或变更表、评审 DDL、给数据消费方写字典。读者要知道「这张表存什么、能怎么查、改它有什么风险」。

## 1. 原则

- **迁移文件和 DDL 是事实源**。文档写 DDL 表达不了的：为什么这样建、每个字段的业务含义、索引服务哪些查询、数据生命周期。
- **注释进库**：表和字段的 `COMMENT` 写在迁移里，数据字典从库里生成，CI 检查文档和 schema 是否漂移。
- **按查询设计，按查询写**：每个索引对应一条真实查询。

## 2. 单表文档要写

模板：`assets/schema-table.md`。

| 项 | 内容 |
|---|---|
| 表名和用途 | 用一句话写清一行代表什么（「一行是一次支付尝试，不是一笔订单」） |
| 归属 | 哪个服务写、哪些服务读；Owner |
| 规模 | 当前行数、日增量、预估一年后 |
| 字段表 | 字段、类型、可空、默认值、约束、含义、示例 |
| 主键和唯一约束 | 以及它们保证的业务规则 |
| 索引 | 每个索引服务的查询（贴 SQL 或接口名） |
| 关系 | 外键或逻辑关联；删除行为（级联、置空、禁止、软删） |
| 枚举和状态 | 每个值的含义；状态机的合法转移 |
| 敏感数据 | PII 字段、加密、脱敏、访问权限 |
| 示例安全 | 字段示例使用合成值或脱敏值；不要把生产 PII、访问凭证或可关联的完整记录贴进字典。 |
| 生命周期 | 保留多久、归档、删除策略 |

字段含义写业务事实，不复述字段名：
- 差：`status` 状态。
- 好：`status` `varchar(16)`，非空，默认 `pending`。支付状态，取值 `pending` → `succeeded` | `failed`；`failed` 可重试回到 `pending`，`succeeded` 为终态。

## 3. 设计检查

- [ ] 主键：自增、UUIDv7 还是业务 ID？对写入热点和分页的影响。
- [ ] 时间：`created_at`/`updated_at` 带时区；用库时间还是应用时间。
- [ ] 金额：整数分或 `decimal(p,s)`，不用浮点。
- [ ] 可空：每个可空字段说明 `NULL` 的业务含义；能非空就非空。
- [ ] 软删：如果有，唯一约束和查询都要考虑 `deleted_at`。
- [ ] 枚举：用字符串还是数字？新增值时的兼容性。
- [ ] JSON 列：里面的结构写在哪？是否需要被查询（需要就拆列或加表达式索引）。
- [ ] 多租户：租户字段在不在每个索引的最左边。

## 4. 索引和查询对应

```markdown
| 索引 | 列 | 服务的查询 | 预估选择性 |
|---|---|---|---|
| idx_orders_user_created | (user_id, created_at DESC) | 用户订单列表 `GET /v1/orders?user_id=` | 高 |
| uq_orders_idem | (tenant_id, idempotency_key) | 下单幂等 | 唯一 |
```

没有对应查询的索引，删掉。

## 5. 迁移说明

线上表变更按 expand/contract 拆步：

1. **Expand**：加新列、新表、新索引（可空或带默认值，不破坏旧代码）。
2. **双写**：代码同时写新旧结构。
3. **回填**：分批迁移存量数据；写清批大小、限速、断点续跑、预计耗时。
4. **切读**：读路径切到新结构，开关控制。
5. **Contract**：确认无读写后删旧列或旧表。

每一步写：

- **DDL 或脚本**（贴出来或给路径）。
- **锁和耗时**：在当前数据量下是否锁表；大表加索引用 `CONCURRENTLY`（PostgreSQL）或在线 DDL 工具（MySQL 的 gh-ost、pt-osc）。
- **验证 SQL**：怎么确认这一步成功（行数对比、空值计数、抽样比对）。
- **回滚**：这一步怎么撤；哪一步之后不可回滚，要标出来。

## 6. 检查清单

- [ ] 一行代表什么，一句话写清。
- [ ] 每个字段：类型、可空、默认值、含义；枚举列全。
- [ ] 每个索引对应一条查询。
- [ ] 删除行为和关联关系写清。
- [ ] PII 和保留期写清。
- [ ] 迁移分步、每步有验证和回滚，不可回滚的步骤标出。
- [ ] 注释已写进迁移文件，字典由 CI 生成或校验。
