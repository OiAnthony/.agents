# 技术方案设计

写可评审的技术方案，或可论证的架构探索文。先选模式，再按对应模板成稿。

## 模式选择（第一步，必做）

| 模式 | 何时用 | 模板 |
|------|--------|------|
| **评审方案** | 要拍板、评审、排期、落地实现 | [`assets/技术方案设计.md`](assets/技术方案设计.md) |
| **架构探索** | 要证明路线说得通、讲清 trade-off、原型验证 | [`assets/架构探索.md`](assets/架构探索.md) |

用户没说清时：问一句「要评审定稿，还是架构探索？」；已给 PRD/排期语境默认 **评审方案**；已给「探索 / 原型 / 像 DeepSeek 那篇」默认 **架构探索**。

两种模式都遵守下方硬规则；文风细则见 [`references/style.md`](references/style.md)。常见模式与图表示例见 [`references/technical-design-reference.md`](references/technical-design-reference.md)。

## 硬规则

1. **先权衡，后模块。** 没有至少一条写清的 Trade-off（选项 / 代价 / 选谁 / 为何），不许开始写模块节。
2. **一节一个结论。** 每节开篇用加粗短断言钉死本节要证明的事；超过两段纯论证就拆节或改成表。
3. **短单句断言。** 一文一事一句；条件与动作进表，不堆长复合句。禁止空泛口号与 GPT 腔过渡段。
4. **图服务论证。** 总架构图的模块编号必须能对上章节；机制节需要示意时再用图（可用 Mermaid；复杂机制可另用 `archify`）。
5. **可检验。** 目标可衡量；探索文的特征清单可逐条对照系统行为；验证测的是架构主张，不是模型智商。
6. **成稿后润色。** 正文稳定后用 `write`（中文）去 AI 味；不要在结构未定前反复打磨句子。

## 工作流程

### Phase 1 · 收集

| 类别 | 必须弄清 |
|------|----------|
| 背景 | 谁在什么约束下做不成什么 |
| 目标 | 做成什么样算成功 |
| 非目标 | 明确不做 |
| 约束 | 技术 / 时间 / 资源 / 合规 |
| 证据 | 现有代码、日志、竞品、失败经历 |

优先读仓库与已有文档；缺关键事实再用问题工具问用户。已有 PRD 时先抽取，不重复盘问。

**完成标准：** 能用一句话写出瓶颈，并能列出 ≥1 条关键 Trade-off。

### Phase 2 · 设计

1. 写下 Trade-off 表（强制）。
2. 画出总架构（或探索文的模块编号总图）。
3. 按模式展开：评审方案写主路径与模块职责；架构探索按「一节一权衡」展开机制。
4. 补风险 / 验证 / 开放问题（探索文必有开放问题）。

**完成标准：** 每个模块能说清输入、输出、明确不做；每张图能用一句话说清它回答的问题。

### Phase 3 · 成稿

按所选模板生成中文文档（代码与专有名词保留英文）。

| | 评审方案 | 架构探索 |
|--|----------|----------|
| 默认文件名 | `技术方案设计.md` 或 `技术方案设计-{功能}.md` | `架构探索.md` 或 `架构探索-{主题}.md` |
| 默认位置 | 项目根或 `/docs` | 同左，或用户指定的探索目录 |

### Phase 4 · 自检与迭代

对照下方清单；不通过则改结构，不先改措辞。初稿交付后按用户意见改，不擅自扩大范围。

## 自检清单

**共用**

- [ ] 开篇有一句话瓶颈或问题
- [ ] 有 Trade-off 表，且推荐有理由
- [ ] 短句为主；条件/动作在表里
- [ ] 图与章节编号对齐
- [ ] 无「赋能 / 全方位 / 值得注意的是」类空话

**仅评审方案**

- [ ] 目标 / 非目标成对出现
- [ ] 主路径有时序或条件→动作表
- [ ] 模块有输入 / 输出 / 不做
- [ ] 风险有应对
- [ ] 可直接拿去评审

**仅架构探索**

- [ ] 3–5 条可检验特征
- [ ] 每节只推一个权衡结论
- [ ] 有验证（实验或可证伪指标）
- [ ] 有开放问题，未假装闭环
- [ ] 原型/仓库指针在文末，正文不是产品说明书
