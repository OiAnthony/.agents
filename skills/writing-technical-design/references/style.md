# 文风与结构细则

配合 `writing-technical-design` 主流程。写正文时遵守；润色阶段交给 `write`。

## 句子

- 默认短单句断言：一文一事一句。
- 条件、分支、例外进表，不写进长复合句。
- 开节先给结论，再给机制；禁止「随着…的不断发展」式起笔。
- 删空话：赋能、闭环生态、全方位、值得注意的是、在本文中我们将。

## 表格优先场景

| 场景 | 用 |
|------|-----|
| 目标与验收 | 目标 / 衡量 |
| 范围裁剪 | 非目标 / 原因 |
| 选型 | Trade-off：选项 / 代价 / 选择 / 为何 |
| 运行逻辑 | 条件 → 动作（→ 结果） |
| 模块边界 | 输入 / 输出 / 不做 |
| 探索特征 | 特征 / 可观察表现 |
| 风险 | 风险 / 影响 / 概率 / 应对 |

## 章节节奏（架构探索）

1. 用加粗断言钉死本节结论。
2. 对照两个极端（表）。
3. 给出机制（角色表 + 可选隐喻一句）。
4. 一张图回答「数据/控制怎么走」。
5. 停止。下一权衡开新节。

## 隐喻

可以借用计算机系统经典思想（Fast/Slow Path、Inline/Spill、存算分离、投机执行、Watchdog），但必须立刻落到本系统的具体角色与数据路径。禁止只扔术语不映射。

## 验证

- 评审方案：验收标准、里程碑、风险应对即可。
- 架构探索：至少一项可证伪指标或实验设计；标明测的是调度/架构还是模型能力。

## 与 DeepSeek Harness 文的对齐点

学：痛点→特征清单→一节一权衡→机制图→实验→开放问题。
不学：默认把句子写长；把探索文写成对外品牌叙事；在正文展开产品操作说明。
